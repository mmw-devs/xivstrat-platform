# 攻略创作平台：业务介绍与交互逻辑

## 1. 平台简介

这是一个面向《最终幻想 XIV》攻略作者的攻略编辑平台。

攻略作者在浏览器中编排副本攻略、撰写图文说明、检查阅读效果，最终生成 JSON 文档：可以下载到本地继续保存，也可以通过提交服务交给审核流程。

编辑平台负责把作者的内容整理成结构化攻略。作者负责游戏机制和解法的准确性；审核方负责判断内容能否接纳；后续发布流程让攻略对读者可见。

```text
作者 ←→ 浏览器中的攻略创作页面
           ├─ 导入／导出 JSON ←→ 作者的本地文件
           ├─ 请求语言校对   ←→ 校对服务 ←→ 配置的模型服务
           ├─ 上传／选择素材 ←→ 图片存储与游戏资源服务
           └─ 提交攻略 JSON  → 提交服务 → GitHub 待审核 PR
                                └─ 提交结果返回作者

待审核内容 → 审核方／后续审核平台 → 后续发布流程 → 攻略读者
```


| 参与方     | 接收或提供什么                  | 职责边界                           |
| ------- | ------------------------ | ------------------------------ |
| 作者      | 输入文字、图片引用、参考链接和宏，选择保存或提交 | 决定攻略内容和组织方式，确认校对修改             |
| 编辑平台    | 呈现表单、正文、预览、校验和操作结果       | 管理当前编辑内容，生成保存／提交所需的数据          |
| 本地文件    | 保存或恢复一份 JSON 内容快照        | 保存与审核互相独立；文件不会自动跟随后续编辑更新       |
| 提交服务    | 接收攻略数据，返回提交结果            | 校验数据、生成目标文件、通过 GitHub 建立待审核 PR |
| 审核方     | 接收待审核内容                  | 决定内容是否接纳；独立审核平台为后续接入方          |
| 校对与素材服务 | 返回语言建议、图片地址或游戏资源         | 按需调用                           |


本地编写、预览和保存不依赖其他服务，数据均在本地。

目前图片存储、选择游戏素材方案还在修改中暂未落地。

提交服务、AI润色接口已有，需要部署到服务器后验证。

## 2. 作者如何完成一篇攻略

### 2.1 开始创作

作者可以从空草稿开始，也可以导入本地 JSON 继续编辑，或载入示例了解结构。

导入成功后，页面根据数据展示导入的基本信息、参考资料、宏、阶段和正文。

注：正文的撤销历史属于当前编辑过程，不随 JSON 保存；重新导入会重建编辑器历史。

### 2.2 编写、检查和交付


| 环节    | 作者操作                         | 页面反馈与结果                             |
| ----- | ---------------------------- | ----------------------------------- |
| 基本信息  | 选择副本类型，填写名称和页面标题，按需设置封面、视频   | 提示名称格式；显示系统管理的状态和操作时间               |
| 参考与宏  | 添加参考链接和游戏宏                   | 保存为整篇攻略的附属资料；宏的空格和换行保持原文            |
| 阶段与机制 | 划分阶段，添加机制或子机制，为其编写说明、解法和注意事项 | 阶段按编号排序；机制、区块及内容可按讲解需要排列            |
| 正文编辑  | 输入文字，使用格式和链接，插入图片            | 在区块内按顺序组织图文；正文支持撤销与重做               |
| 全文校对  | 阅读完整正文；按需请求 AI 建议，逐条接受或忽略    | 建议定位到对应正文；接受后更新正文，失效或无法准确定位的建议不自动应用 |
| 预览与校验 | 查看阅读效果和字段错误，返回编辑修正           | 预览和校验读取当前编辑内容；语言建议不代替内容完整性校验        |
| 保存到本地 | 点击保存 JSON                    | 记录本次保存时间并发起下载；未完成的草稿也可保存            |
| 提交审核  | 在内容符合提交要求后发起提交               | 服务端复核并建立待审核 PR；页面显示成功凭据或失败信息        |


提交成功时，显示 PR 链接和提交标识。表示已进入待审核流程。

注：保存到本地和提交审核是两个独立出口，作者不必先下载再提交。

注：保存提示“已发起下载”时，作者仍需确认浏览器实际保存了文件。

### 2.3 出错时如何继续


| 情况           | 作者看到什么、如何处理                        |
| ------------ | ---------------------------------- |
| 必填项未完成或名称不合法 | 页面指出字段和原因；继续编辑或先保存草稿，符合要求后再提交      |
| JSON 导入失败    | 显示错误，原有编辑内容不被替换                    |
| 校对或素材服务不可用   | 显示该功能的错误，作者可继续编辑                   |
| 审核提交明确失败     | 显示失败原因和是否允许重试；作者仍可本地保存             |
| 审核提交结果不确定    | 明确说明无法确认远端结果，阻止直接重复提交，先核实是否已产生远端内容 |


## 3. 攻略内容如何划分

### 3.1 阶段、机制、区块分别是什么


| 层级   | 作者用它回答的问题          | 划分方式与内容边界                                               |
| ---- | ------------------ | ------------------------------------------------------- |
| 基本信息 | 这是哪个副本？            | 一篇攻略对应一个副本，包含副本名、副本类型、参考资料和宏                            |
| 阶段   | 战斗进行到哪一大段？         | 作者按战斗流程分段，例如前半、转场、本体。编号规则见 5.2                          |
| 机制   | 这一段需要理解和处理什么事件？    | 一个可独立讲解的事件或连续组合，例如某次点名处理、一次运动会式组合；放在所属阶段下               |
| 子机制  | 这个机制里有什么值得单独讲解的环节？ | 从复杂机制中拆出的处理环节，例如运动会中如何单独处理踩塔、分摊、连线；需要单独标题或图文说明时使用，可继续嵌套 |
| 区块   | 分为机制、解法、注意三种       | 在一个机制内部按用途组织说明；同一机制可有多个区块                               |
| 内容块  | 分为文字、图片两种          | 在一个区块内部，文字和图片可以按顺序混排                                    |


“机制”介绍这个机制是什么、发生了什么及其规则，“解法”回答玩家怎么做，“注意事项”补充风险或易错点。它们都能包含文字和图片。

### 3.2 对应的数据关系

```text
攻略
├─ metadata：整篇攻略的基本信息
├─ references[]：全局参考资料
├─ macros[]：全局游戏宏
└─ phases[]：阶段
   ├─ name：阶段编号与可选中文标题
   └─ mechanics[]：机制
      ├─ name：机制名称
      ├─ sections[]：区块
      │  ├─ type：mechanic / solution / note
      │  ├─ title：区块标题
      │  └─ content[]：正文或图片，按阅读顺序排列
      │     ├─ 正文：type=text，id，doc
      │     └─ 图片：type=image，file，caption
      └─ sub_mechanics[]：子机制，结构与机制相同
```

`[]` 表示数组。参考资料和宏属于整篇攻略，不属于某个阶段。正文中的稳定 id 由系统管理，用于校对定位，移动正文时保持不变。

## 4. 数据交互


| 交互      | 传入              | 传出与效果                                            |
| ------- | --------------- | ------------------------------------------------ |
| 导入攻略    | 作者选择的 JSON 文件   | 检查后恢复为可编辑草稿；失败不替换当前内容                            |
| 本地保存    | 当前编辑内容          | JSON 文件下载；包含本次保存时间，不包含编辑器撤销历史                    |
| 提交审核    | 当前攻略数据          | 提交服务生成 JSON、通过 GitHub 写入目标文件并创建 PR，返回 PR 链接与提交标识 |
| 全文校对    | 正文、层级标题上下文及术语偏好 | AI校对提供语言建议；不发送图片、宏、参考链接。作者手动决定是否采用               |
| 上传或选取素材 | 图片文件或资源查询条件     | 可用于封面和正文的图片引用；JSON 保存地址或相对路径，图片资源由相应存储提供（暂未实现）   |


编辑、预览、本地保存和提交读取同一份当前内容。

提交服务负责生成目标文件路径及操作时间。当前审核交接载体是 GitHub PR；后续独立审核平台承接审核工作，编辑平台页面仍负责提供待审核的攻略数据。

## 5. 创作与提交规则

### 5.1 名称与身份


| 对象     | 标识                   | 唯一性范围           | 行为                                                   |
| ------ | -------------------- | --------------- | ---------------------------------------------------- |
| 副本攻略   | metadata.name        | 固定内容目录内唯一       | 生成的JSON文件名，由副本英文名生成。同名提交更新同一文件；暂不支持一副本多篇独立攻略或已有文件重命名 |
| 阶段     | phases[].name 中的数字 | 整篇攻略            | 数字决定阶段顺序；中文标题只用于说明                                   |
| 机制及子机制 | name                 | 同一阶段内，包含所有递归子机制 | 不同阶段可以重名；英文区分大小写                                     |
| 正文块    | 系统生成的 id             | 整篇攻略            | 供校对定位；移动正文块时保持不变，作者不可编辑                              |


副本名称按 metadata.type 校验：


| 类型           | metadata.name 规则              | 示例                       |
| ------------ | ----------------------------- | ------------------------ |
| savage（零式）   | 一个小写英文字母 + 1–12 的整数 + 字符 s    | `o4s`、`p8s`、`e12s`、`m1s` |
| extreme（极神）  | 英文小写全名，以短横线连接单词；禁止空白及短横线以外的标点 | `the-unmaking`           |
| ultimate（绝本） | 同 extreme                     | `the-epic-of-alexander`  |
| other（其他）    | 暂时同 extreme                   | 同上                       |


零式格式为 `^[a-z](?:[1-9]|1[0-2])s$`。极神、绝本及 other 的名称输入中，普通空格（U+0020）自动替换为 `-`，结果显示给作者，并用于保存、提交和文件命名；其他 Unicode 空白和控制字符仍报错。撇号、括号等标点禁止输入，不自动删除；大写字母不自动转小写。此转换仅适用于这三类副本名称。

服务端根据副本 name 在 `content/strategies/` 下生成 JSON 文件路径，校验路径分隔符、路径穿越、非法文件名和 Windows 保留名。客户端不能指定任意文件路径。副本名称最长 120 个字符。改变 name 会改变目标文件，界面须明确提示，不作为文件重命名操作。

### 5.2 阶段名称

阶段名称由三个部分拼接：<strong>字符 p + 数值编号（整数或 .5 小数）+ 可选中文标题</strong>。

```text
name = "p" + 编号 + ["-" + 中文标题]
```

编号是数值，允许整数及小数部分为 .5 的数。以下规则同时约束其文本写法：


| 项目    | 规则                                      |
| ----- | --------------------------------------- |
| 数值范围  | 0.5–10.5，步长 0.5；整数部分上限为 10              |
| 编号写法  | 整数写为 1、2、…、10；半阶段写为 0.5、1.5、…、10.5；无前导零 |
| 中文标题  | 可省略；填写时至少一个汉字，仅使用汉字及 `·、，（）`            |
| 标题分隔符 | 有标题时使用一个短横线连接，如 p1-卡夫卡                  |
| 排序与重复 | 按编号数值升序排列，并在全篇检查编号唯一                    |


例：`p1`、`p1-卡夫卡`、`p1.5-转场`。`p1-甲` 与 `p1-乙` 编号相同，不能同时存在。

阶段名称整体保存为 name，数字部分用于排序和校验。

### 5.3 字符规则

普通字符串字段禁止 Unicode 空白和控制字符，包括普通空格、制表符、换行、全角空格以及零宽空格、BOM 等不可见格式控制字符。规则覆盖名称、标题、图片说明、地址等字段。

两个例外：正文富文本的文本内容，以及 macros[].code。正文按富文本契约校验；宏 code 保留原文，包括空格和换行。

除 5.1 明确允许的副本名称空格转短横线外，违规值应报告字段路径和原因，不自动去空白、改大小写或清洗字符。JSON 自身的缩进与换行不属于字段值。

### 5.4 草稿与正式提交

草稿允许内容未完成。编辑器提示字段错误，本地保存不以“提交必填条件”阻断操作；损坏的数据结构和不安全输入仍拒绝。

正式提交须满足字段表中的约束，并满足以下内容完整性要求：

- 至少一个阶段，每个阶段至少一个机制。
- 叶子机制至少一个区块，每个区块至少一个内容块。
- 正文至少含非空白文字；图片必须有 file，caption 可空。
- 参考资料和宏可不添加；添加条目后，其两个字段均需填写。

阶段排序由编辑器及输出流程执行；未完成的阶段名保留并提示。服务端按相同规则复核提交内容。

### 5.5 状态与操作时间

metadata.status 保留 draft、review、done 三种共享状态。本版编辑器的状态固定为 draft，只读展示；导入 review/done 时提示“作为草稿编辑”并转为 draft。当前提交接口仅接受 draft；后续审核平台负责其他状态流转。

metadata.publish_time 表示本次本地保存或提交审核的时间。系统在每次操作时生成并写入该次 JSON，作者不能手动填写：


| 操作        | 时间来源         | 输出格式                                     |
| --------- | ------------ | ---------------------------------------- |
| 保存本地 JSON | 设备当前时间       | 带时区 ISO 8601，例如 2026-09-19T08:30:00.000Z |
| 提交审核      | 服务端受理本次提交的时间 | 同上；服务端生成，不直接信任客户端时间                      |


未发生操作的新草稿可以没有时间值。再次保存或提交使用新的时间；导入文件中的旧时间不能替代它。该字段记录操作时点，不证明下载落盘、审核通过或部署完成。

## 6. 平台边界

- 每个副本暂时只对应一篇独立攻略；支持在其中组织不同解法，不提供多个独立攻略文件或已有文件重命名。
- 草稿可不完整；提交要求内容完整且字段合法。结构检查和语言校对都不保证游戏机制及解法正确，仍需作者和审核方判断。
- 本地保存是主动下载，不是持续自动保存；页面后续修改不会同步到已下载文件，也不承诺关闭页面后自动恢复。
- 编辑器使用 draft 状态。review/done 供后续审核平台使用，提交 PR 不自动等于状态已进入 review 或 done。
- 图片引用不保证对应资源永久可访问；本地 JSON 不是包含全部图片资源的离线包。
- 本文覆盖创作、预览、草稿文件和审核交接；审核裁决、合并、上线发布以及生产服务部署由对应流程负责。

运行环境与服务配置见 [README](../README.md)；模块职责见 [编辑器架构](editor-architecture.md)；校对服务及建议处理细节见 [正文编辑与全文校对](richtext-proofread.md)。

## 附录 A：攻略 JSON 数据说明

下表用于对照编辑内容与 JSON 数据。M 表示任意层级机制，S 表示区块，C 表示内容块。“必填”指正式提交；空字符串可用于尚未填写的草稿字段。通用字符规则见 5.3。

### A.1 根对象和基本信息


| 字段                     | 类型     | 用途与要求                                                              |
| ---------------------- | ------ | ------------------------------------------------------------------ |
| metadata               | object | 攻略基本信息                                                             |
| phases                 | array  | 阶段；提交至少一项                                                          |
| references             | array  | 参考资料，可为空                                                           |
| macros                 | array  | 游戏宏，可为空                                                            |
| metadata.name          | string | 副本名称及文件标识，必填；规则见 5.1                                               |
| metadata.type          | enum   | 必填：extreme（极神）/ savage（零式）/ ultimate（绝本）/ other（其他）；决定 5.1 的副本名称规则 |
| metadata.title         | string | 页面标题，必填                                                            |
| metadata.banner        | string | 封面，选填；项目相对路径或 http/https 地址                                        |
| metadata.video         | string | 视频，选填；http/https 地址                                                |
| metadata.status        | enum   | 编辑器固定 draft；流转边界见 5.5                                              |
| metadata.publish_time | string | 自动操作时间；生成规则见 5.5                                                   |


图片和封面地址应拒绝路径穿越及危险协议；选填字段有值时仍需合法。

### A.2 阶段、机制和内容


| 字段                   | 类型     | 用途与要求                                    |
| -------------------- | ------ | ---------------------------------------- |
| phases[].name      | string | 阶段组合名称，必填；规则见 5.2                        |
| phases[].mechanics | array  | 本阶段机制                                    |
| M.name               | string | 机制名称及标识，必填                               |
| M.sections           | array  | 当前机制的区块                                  |
| M.sub_mechanics     | array  | 递归子机制，可为空                                |
| S.type               | enum   | mechanic（机制说明）/ solution（解法）/ note（注意事项） |
| S.title              | string | mechanic/solution 必填，note 可空             |
| S.content            | array  | 按展示顺序排列的正文或图片块                           |
| C.type               | enum   | text / image；区别于区块角色 S.type              |
| C.id（正文）             | string | 全篇唯一，系统生成，长度 1–100；见 5.1                 |
| C.doc（正文）            | object | 受限富文本文档；见 A.4                            |
| C.file（图片）           | string | 必填；项目相对路径或 http/https 地址                 |
| C.caption（图片）        | string | 图片说明，选填                                  |


### A.3 参考资料与宏


| 字段                   | 类型     | 用途与要求                    |
| -------------------- | ------ | ------------------------ |
| references[].label | string | 资料标题，有条目时必填              |
| references[].url   | string | 资料地址，有条目时必填；http/https   |
| macros[].name      | string | 宏名称，有条目时必填               |
| macros[].code      | string | 宏原文，有条目时必填；不 trim、不替换或清洗 |


### A.4 富文本

每个 doc 包含段落，每个段落包含文本或换行节点。文本可以附带格式。以下路径相对于 C.doc：


| 字段                      | 契约                                                    |
| ----------------------- | ----------------------------------------------------- |
| type                    | 固定 doc                                                |
| content[]             | 1–5000 个段落                                            |
| content[].type        | 固定 paragraph                                          |
| content[].content[] | 行内节点数组，可省略或为空                                         |
| …行内节点.type              | text / hardBreak                                      |
| …行内节点.text              | text 节点必需的非空字符串；hardBreak 无此字段                        |
| …行内节点.marks[]         | text 节点的可选格式，最多 6 个，类型不重复                             |
| …marks[].type         | bold / italic / underline / strike / link / textStyle |
| …marks[].attrs        | link/textStyle 使用；四种基础格式不使用                           |
| …attrs.href             | link 必填；http/https/mailto，最长 2000，无空白、控制字符及凭据         |
| …attrs.color            | textStyle 选填；限定下述调色板                                  |
| …attrs.fontSize         | textStyle 选填；16px / 20px / 24px                       |


调色板：#f87171、#facc15、#4ade80、#60a5fa、#c084fc。单正文块最多 20000 个行内节点、200000 个文本字符；未知富文本字段和节点被拒绝。hardBreak 只包含 type。
